# MEB Gateway Energy — Passive Bluetooth Capture (2026-10-15)

## Purpose

Passively capture Car Scanner's Bluetooth Classic traffic while it reads two
existing `[19.Gate]` measurements, to determine the app's actual ELM commands,
responses, response addressing, and raw diagnostic data — and to check whether
the configured request header `710` / receive filter `77A` path is real.

This is a **passive** capture. No diagnostic traffic was generated by any
script or tool. The only live vehicle activity was normal Car Scanner use while
Android's Bluetooth HCI snoop logging was enabled.

## 5. Observed ELM command / response evidence

The log contains the full ELM ASCII conversation over RFCOMM (a Bluetooth
Serial Port Profile). Direction was derived from the BTSnoop ACL packet flag
bit 0 (0 = Host→Controller/sent, 1 = Controller→Host/received), validated
against HCI Reset (sent) and its Command Complete event (received).

### 5.1 Request path — `710` / `77A` is used

The `[19.Gate]` energy reads use 11-bit CAN (protocol 6) with request header
`710` and receive filter `77A`:

```
ATSH710      set header 710            (Host→Ctrl)
ATSP6        protocol 6 (ISO15765-4 11-bit 500k)
ATFCSH710    flow-control header 710
ATCRA77A     receive filter 77A
222AB8       read DID 0x2AB8
```

`ATSH710`, `ATFCSH710`, and `ATCRA77A` are all present verbatim, and every
response line begins with the CAN id `77A`. This **confirms** the configured
`710` request header and `77A` receive filter.

Note on ordering: the flow-control setup `ATFCSD300000` (data `30 00 00`) and
`ATFCSM1` (mode 1) are issued once during an earlier 29-bit functional-scan
phase (`ATSHFC007B` / `ATCRA17FE007B` / `ATFCSH17FC007B` / `ATSP7`), not
immediately before each `710` read. The essential per-read sequence is
`ATSH710` → `ATSP6` → `ATFCSH710` → `ATCRA77A` → `222AB8`.

Also note the request is sent as `222AB8` (concatenated hex, no space), i.e.
`22 2A B8` — equivalent to the profile's `22 2A B8`.

### 5.2 DID `0x2AB8` — positive response, value matches

Request (raw bytes):

```
32 32 32 41 42 38 0D          "222AB8\r"
```

Response (two ELM lines, both `Ctrl→Host`, same timestamp):

```
77A100B622AB8000005\r        CAN 77A, First Frame
77A217F00000000AAAA\r        CAN 77A, Consecutive Frame
```

ISO-TP reassembly (message length `0x0B` = 11 bytes):

```
62 2A B8 00 00 05 7F 00 00 00 00
|  |  |  |___________|
SID DID data (8 bytes)
```

- SID `62` = positive response to ReadDataByIdentifier.
- DID `2A B8`.
- data = `00 00 05 7F 00 00 00 00`.
- Profile: start index 2, length 2 → bytes `05 7F` = `0x057F` = 1407.
- 1407 × 25 Wh/LSB = **35 175 Wh** → matches the displayed value **exactly**.

(The trailing `AAAA` is the ELM327's padding for unused nibbles, not payload.)

A second, earlier `0x2AB8` read in the same session returned `05 80` = 0x0580 =
1408 → 35 200 Wh, i.e. the value drifted by 25 Wh between refreshes, as
expected for a live reading.

### 5.3 DID `0x2AB2` — positive response, value matches

Request (raw bytes):

```
32 32 32 41 42 32 0D          "222AB2\r"
```

Response (single ELM line, `Ctrl→Host`):

```
77A07622AB204280400\r        CAN 77A, Single Frame
```

- Single frame PCI `07` (7 data bytes): `62 2A B2 04 28 04 00`.
- SID `62` = positive response; DID `2A B2`; data = `04 28 04 00`.
- Profile: start index 0, length 2 → bytes `04 28` = `0x0428` = 1064.
- 1064 × 50 Wh/LSB = **53 200 Wh** → matches the displayed value **exactly**.

## 7. What the capture proves

1. **Profile configuration confirmed** — request header `710` (`ATSH710`,
   `ATFCSH710`) and receive filter `77A` (`ATCRA77A`) are genuinely used, on
   `ATSP6` (11-bit, 500 kbit/s).
2. **Live ELM command sequence observed** — including `222AB8` and `222AB2`.
3. **Positive diagnostic response observed** — SID `62` for both DIDs, arriving
   with CAN id `77A`.
4. **Raw diagnostic payload independently extracted**:
   - `0x2AB8` → `62 2A B8 00 00 05 7F 00 00 00 00`
   - `0x2AB2` → `62 2A B2 04 28 04 00`
5. **Proposed decoder validated** — applying the profile's offsets/multipliers
   reproduces the contemporaneous displayed values exactly:
   - `0x2AB8`: data[2:4] `05 7F` = 1407 × 25 = **35 175 Wh** ✓
   - `0x2AB2`: data[0:2] `04 28` = 1064 × 50 = **53 200 Wh** ✓

### Model A status

**Model A is validated.** The captured payloads support applying the profile
offsets and multipliers (`0x2AB8` start 2 / len 2 / ×25; `0x2AB2` start 0 /
len 2 / ×50) to produce values consistent with Car Scanner's displayed
readings. "Start index" is interpreted as relative to the data bytes that
follow SID+DID, which is the only interpretation consistent with both values.

## 8. What the capture does not prove

The snoop log is **Bluetooth HCI + RFCOMM** traffic. It contains the ELM327's
**ASCII** command/response strings, not raw CAN frames:

- The actual CAN frames on the vehicle bus (e.g. `710 03 22 2A B8` request and
  the raw `77A` frames) are **not** in this capture — they exist only on the
  adapter's CAN transceiver, invisible to the phone's Bluetooth radio.
- The `77A` seen in responses is the ELM reporting the received CAN id (header
  mode on / `ATCRA77A`), i.e. strong but indirect evidence of the receive
  addressing, not a raw CAN frame capture.
- The `710` request header is confirmed by the ELM being told to use it
  (`ATSH710`), not by observing the on-bus frame itself.

Therefore claims 1–5 above are verified **at the ELM command/response level**;
the raw CAN bus framing is inferred, not directly captured.

## 9. Remaining uncertainties / next steps

- **Not addressed here**: why earlier project tests did not reproduce Car
  Scanner's result despite using `710`/`77A`. This capture shows the app does
  use `710`/`77A` with `ATSP6`, concatenated-hex requests (`222AB8`), and
  expects the ELM's multi-line First-Frame + Consecutive-Frame output. A
  follow-up should compare the project's exact ELM command string, flow-control
  setup (`ATFCSD300000` / `ATFCSM1`), and response-reassembly logic against the
  exact bytes in §5.
- **Wall-clock correlation** is approximate (relative BTSnoop timestamps +
  log-span vs. bug-report time), not a per-frame wall-clock stamp.
- **Safest next step**: diff the project's ELM init sequence and multi-frame
  reassembly against the captured sequence, with **no** live vehicle traffic —
  ideally by replaying the captured ASCII into a bench/test ELM simulator.
