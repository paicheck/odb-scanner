# ODB Scanner — Android app

The Android companion to the Python `odb_scanner` collector. It speaks the same
read-only UDS protocol to the same ELM327 adapter over classic Bluetooth SPP,
and decodes the same DID map — because both are driven by one shared spec.

```
spec/odb_scanner.json  <-  generated by tools/export_spec.py (single source of truth)
        |
        +--> Python collector (Windows)     reads it at build time via the live registry
        +--> Android app (this directory)   bundles it in assets/spec.json
```

## What it does

* **Bluetooth SPP transport** — `transport/BluetoothSpp.kt` (RFCOMM socket) +
  `transport/Elm327Protocol.kt` (ELM327 AT commands + the per-ECU addressing
  quirks the v1.5 clone needs: `ATCAF1`+bare request+flow-control for every
  physical module, 11-bit and 29-bit alike; a hand-framed `ATCAF0` line is
  refused with `?`).
* **Read-only guard** — `uds/ReadOnlyGuard.kt` enforces the exact allow-list
  from the spec (`uds.py`'s `validate_request`, verbatim: service, sub-function,
  length limits). Nothing reaches the bus without passing through it.
* **DID read + decode** — `uds/Uds.kt` (ISO-TP reassembly + NRC) and
  `spec/Decode.kt` (scalar arithmetic + the named special decoders).
* **Collection loop** — `collect/Collector.kt` (discovery, VIN read at connect,
  polling, and the NRC-0x31 / silent-DID retirement that stops re-polling dead
  DIDs). The fast DIDs run every pass; the slow DIDs — including all 108 cell
  voltages, which are ordinary spec measurements — run on their own 60 s
  cadence so a pass stays quick.
* **Persistence** — Room (`db/`), mirroring the Python SQLite schema
  (`measurements`, `tx_log`, `unsupported_dids`, `vehicles`). Non-scalar decodes
  (the `vin` string, `gear`, and the structured `pair`/`energy_counters` maps)
  are written to `text_value` as JSON with a NULL numeric `value`, matching
  `collector.py`/`cloud/mapping.py`. Every read is mirrored to `tx_log` as a
  TX/RX pair, so "read-only" is auditable after the fact.
* **Cloud upload** — `net/CloudSync.kt` posts new measurements to the shared
  cloud ingest API in batches (see `../cloud/README.md`). It is offline-first:
  each row carries a UUID assigned at write time (`remoteId`), and it is marked
  uploaded (`uploadedAt`) only after the API acknowledges it, so a failed or
  interrupted upload is simply retried. Configure the URL and token under
  **Cloud settings** in the app; the token is a revocable ingest credential,
  never a database password.
* **UI** — `MainActivity.kt` (Jetpack Compose): connect, discover, collect,
  list decoded values, and sync to the cloud.

## Build

Open `android/` in Android Studio (or run `./gradlew assembleDebug` after
generating a wrapper). It targets:

* `compileSdk 34`, `minSdk 26` (Android 8.0+)
* Kotlin 2.0, Jetpack Compose, Kotlin coroutines

`spec.json` is bundled in `app/src/main/assets/`. Regenerate it after any DID
or decode change in the Python repo — `--sync-android` writes both files from
one run so they cannot drift:

```powershell
python tools/export_spec.py --sync-android
```

CI enforces this: `tests/test_spec_export_in_sync.py` fails if the committed
spec is stale or the asset differs from it.

## Route planner and Android Auto

**Route** (main screen) plans an electric trip from the phone's position (or a
typed start): arrival charge, charging stops and journey time, using the
battery figures the phone last read from the car. It is the dashboard's
planner ported line for line (`route/Planner.kt`); `PlannerTest` holds it to
the same `tests/data/route_vectors.json` cases as the Python side, so both give
the same plan. The trip is drawn on an OpenStreetMap map in the app (tiles of
the trip area are fetched from OpenStreetMap); **Start navigation** navigates
it in the app, turn by turn (below). **Open in Google Maps instead** hands the
whole trip to Google Maps, charging stops as stops and then the destination;
Route → Settings can make Google Maps the default.

**Traffic and roads to avoid.** With a Mapbox token (optional, Route →
Settings; a free mapbox.com account gives 100,000 route requests a month) the
planner asks Mapbox for routes in today's traffic: the recommended way and up
to two others, each with its driving time now, how much slower than usual that
is, and how much of it is heavy traffic. **Use** on another way plans the
charging stops on that one. Mapbox gives no heights, so OpenRouteService adds
them (the hills still count). **Avoid motorways / tolls / ferries** apply to
both services. Without a token: OpenRouteService's one route, no traffic.

**Navigation.** Turn by turn on the phone: the next turn with its distance,
an arrow, the road and the exit; the lanes to be in, lit up; a heading-up map
of the road ahead with heavy traffic in orange and very heavy in red; with
a Mapbox token, the posted speed limit as a sign beside your speed (red once
you are past it by 10% plus 2 mph, when it also says the limit, once for that
stretch); the arrival time (including charging), the charge you should arrive
with (re-planned from the car's battery as you drive), and what traffic adds. It speaks each turn
in British English -- "In a quarter of a mile, take the ramp on the left
towards the M40. Use the left two lanes." -- warns of heavy traffic about
three km ahead, and re-routes when you leave the route. Tap the instruction to
hear it again; **Mute**; **Route** checks for a faster way, changes the roads
to avoid, re-plans the charging or opens Google Maps; **End** ends the trip.
**Back** leaves it running: still spoken, with the next turn in the
notification. One leg at a time: to the first charging stop (where it says how
far to charge), on when you drive off, then to the destination. With Mapbox,
every five minutes it checks today's traffic and takes a way that saves at
least five minutes (and a tenth of the time left), saying so.

Lanes and the ready-made spoken sentences come from Mapbox; without a token
the app makes the spoken turns itself from OpenRouteService's steps, with no
lanes or traffic. `NavTest` follows a drive along a recorded Mapbox reply
(`tests/data/mapbox_route_sample.json`, also read by the dashboard's tests);
`NavigatorDeviceTest` drives it on an emulator through the real GPS pipeline
and speech. Not yet tried on the road.

**Which stops.** Every fast charger within 5 km of the route is a candidate;
the planner picks the stops, and how far to charge at each, for the lowest
price plus time. **Fastest** counts time as everything; **Balanced** counts it
at your own £/hour (Route → Settings, default 15); **Cheapest** counts it at
only £3/hour, so it will not add a stop to save pennies. Each stop also costs
10 minutes and its detour, and adds at least 10 %. Prices: what you pay per
network ("Ionity = 0.39" lines in Route → Settings) beats the price Open
Charge Map lists, which beats the default for unknown prices. Tesla-only,
private and out-of-service chargers are left out.

**Re-planning while driving.** Start navigation also starts watching the trip.
Every minute the phone compares the car's latest charge reading (stored by the
collector) with what the plan expected where the phone is now. Three % below
plan, five above, four km off the planned road, or charging just finished:
it re-plans from here -- first correcting the consumption figure by what this
drive is really using -- and notifies you if the stops change. It never
re-plans while charging, near a planned charger, on a reading over 15 minutes
old or a position over 3 minutes old, or more often than every 5 minutes.
**Re-plan now** and **End trip** are on the planner (and the car screen).

Following a trip needs **precise location**, asked for once when you start one:
approximate location is ~2 km off and refreshed only every ~10 minutes. While
the trip runs, a "Watching your trip" notification stays up -- that
location-type foreground service is what lets the phone read its position
with the screen off (or Google Maps in front), and it ends at arrival or End
trip. Without precise location there are no turn-by-turn directions and only
Re-plan now works.

It needs two free API keys, entered under **Route → Settings**:
[OpenRouteService](https://openrouteservice.org/dev/#/signup) (roads, place
search, heights) and [OpenChargeMap](https://openchargemap.org/site/profile/applications)
(chargers). The start, destination and route are sent to those two services --
and, with a Mapbox token, the start, the next stop and the destination to
Mapbox (while navigating, the current position with each new route). Location
permission (coarse) is asked only when you plan without a typed start.

**Android Auto** shows these screens on the car display — **Battery** (newest
stored readings with their age), **Route planner** (the active trip, recent
destinations, search, then the plan with its costs; Navigate starts the
directions, Re-plan / End trip while driving), **Navigation** (the next turn,
the lanes, traffic ahead and the arrival time, as text -- tap Next to hear it
again; Mute, End), **Fault codes** and **Assistant** — built from the Car App
Library's driver-safe templates (`car/`). They read the phone's database and
never reach the adapter. Because the app is not from the Play Store, Android
Auto lists it only with developer settings on:

1. Android Auto settings on the phone → tap **Version** ten times → developer
   settings → enable **Unknown sources**.
2. Install the APK, open the app once, set the route keys.
3. Connect to the car; *ODB Scanner* appears in the launcher.

The app is declared in the **charging** category, the closest Android Auto has
to a trip planner; a Play Store release would need Google's review of that
choice. Only navigation-category apps may draw a map on the car display, so
there the directions are spoken, with the text screen as back-up. The car screens could not be tried on a real head unit while building
them; the Desktop Head Unit (`desktop-head-unit` in the SDK's
`extras/google/auto`) is the way to try them on a computer.

## AI assistant

**Ask AI** (main screen) and **Assistant** (car screen) answer questions about
the car and the trip, typed or spoken. Choose the AI service under Ask AI ->
Settings: **Claude** (through Anthropic's Java SDK; `claude-opus-5-5` unless
you pick another model), **OpenAI, Google Gemini, Mistral, Groq, OpenRouter,
DeepSeek, xAI**, or any OpenAI-compatible https endpoint. Each needs your own
API key from that service (billed per use); keys are stored encrypted with a
key held in the Android Keystore.

What it can do -- all read-only, nothing reaches the car: read the stored
battery readings, fault codes and any measurement with its history; describe
the trip being driven (stops ahead, charge, cost, the road each is on); read
out the route's turn-by-turn steps ahead (junctions, exits, lanes); while
navigating, the next turn, the arrival time and traffic ahead; find chargers
near you with prices; plan or re-plan a trip; start navigation; re-route
("avoid the motorway", "is there a faster way?"). What is
sent to the service: your question and what those tools return -- never the
VIN, never your exact position.

**Voice.** Speak asks one question through the phone's speech recogniser and
answers aloud (as navigation guidance: music ducks; with Android Auto it plays
through the car). Trip alerts are spoken too, as fixed sentences that cost no
AI request: a charging stop about five miles ahead, a re-plan that changes the
stops, a charge below plan.

**Wake word** (off by default). With it on, the phone listens for "hey
scanner" (or your phrase) using Vosk on the phone itself -- a 40 MB model,
downloaded once; no audio leaves the phone until the phrase is heard. A
notification shows while it listens, with Stop. It uses some battery, so it
suits a phone on the car charger. Tested: the real Vosk engine on an emulator
against recorded speech (`connectedDebugAndroidTest`); not yet with a live
microphone in a car.

In the car the microphone is the phone's own; Android Auto's car microphone
is not used. The car screens and voice have not been tried on a head unit.

## Versioning

The app version is one number, stored once: `version.json` at the repo root.
Both the Python CLI (`main.py --version`, `version.__version__`) and this app
(`build.gradle.kts`) read it, so a release bump is a single edit:

* `versionName` = the string in `version.json` (e.g. `0.2.0`);
* `versionCode` is derived from it — `MAJOR*10000 + MINOR*100 + PATCH` (so
  `0.2.0` → `200`) — and must only ever be a monotonically increasing integer,
  which is why it is computed rather than hand-maintained.

To release, bump `version.json` and rebuild; never edit the numbers in
`build.gradle.kts`. Two other version strings exist and are deliberately
separate: `spec.json`'s `spec_version` (the data-schema / allow-list version)
and `CATALOGUE_VERSION` (the decoder catalogue). `tests/test_versioning.py`
pins all of this.

## Safety (non-negotiable)

This app is **strictly read-only**. The only requests it can send are the
allow-listed ones in `spec.json` (`0x10 0x01`, `0x22`, `0x19` read sub-functions,
`0x3E`, OBD-II `0x01/0x03/0x09`). `uds/ReadOnlyGuard.kt` is the choke point and
must never be weakened; a port must not add a "send arbitrary bytes" API.
