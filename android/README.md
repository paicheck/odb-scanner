# ODB Scanner — Android app

The Android companion to the Python `odb_scanner` collector. It speaks the same
read-only UDS protocol to the same ELM327 adapter over classic Bluetooth SPP,
and decodes the same DID map — because both are driven by one shared spec.

```
spec/odb_scanner.json  <-  generated by tools/export_spec.py (single source of truth)
        |
        +--> Python collector (Windows)     reads it at build time via the live registry
        +--> Android app (this directory)   bundles it in assets/spec.json
```

## What it does

* **Bluetooth SPP transport** — `transport/BluetoothSpp.kt` (RFCOMM socket) +
  `transport/Elm327Protocol.kt` (ELM327 AT commands + the per-ECU addressing
  quirks the v1.5 clone needs: `ATCAF1`+bare request+flow-control for every
  physical module, 11-bit and 29-bit alike; a hand-framed `ATCAF0` line is
  refused with `?`).
* **Read-only guard** — `uds/ReadOnlyGuard.kt` enforces the exact allow-list
  from the spec (`uds.py`'s `validate_request`, verbatim: service, sub-function,
  length limits). Nothing reaches the bus without passing through it.
* **DID read + decode** — `uds/Uds.kt` (ISO-TP reassembly + NRC) and
  `spec/Decode.kt` (scalar arithmetic + the named special decoders).
* **Collection loop** — `collect/Collector.kt` (discovery, VIN read at connect,
  polling, and the NRC-0x31 / silent-DID retirement that stops re-polling dead
  DIDs). The fast DIDs run every pass; the slow DIDs — including all 108 cell
  voltages, which are ordinary spec measurements — run on their own 60 s
  cadence so a pass stays quick.
* **Persistence** — Room (`db/`), mirroring the Python SQLite schema
  (`measurements`, `tx_log`, `unsupported_dids`, `vehicles`). Non-scalar decodes
  (the `vin` string, `gear`, and the structured `pair`/`energy_counters` maps)
  are written to `text_value` as JSON with a NULL numeric `value`, matching
  `collector.py`/`cloud/mapping.py`. Every read is mirrored to `tx_log` as a
  TX/RX pair, so "read-only" is auditable after the fact.
* **Cloud upload** — `net/CloudSync.kt` posts new measurements to the shared
  cloud ingest API in batches (see `../cloud/README.md`). It is offline-first:
  each row carries a UUID assigned at write time (`remoteId`), and it is marked
  uploaded (`uploadedAt`) only after the API acknowledges it, so a failed or
  interrupted upload is simply retried. Configure the URL and token under
  **Cloud settings** in the app; the token is a revocable ingest credential,
  never a database password.
* **UI** — `MainActivity.kt` (Jetpack Compose): connect, discover, collect,
  list decoded values, and sync to the cloud.

## Build

Open `android/` in Android Studio (or run `./gradlew assembleDebug` after
generating a wrapper). It targets:

* `compileSdk 34`, `minSdk 26` (Android 8.0+)
* Kotlin 2.0, Jetpack Compose, Kotlin coroutines

`spec.json` is bundled in `app/src/main/assets/`. Regenerate it after any DID
or decode change in the Python repo — `--sync-android` writes both files from
one run so they cannot drift:

```powershell
python tools/export_spec.py --sync-android
```

CI enforces this: `tests/test_spec_export_in_sync.py` fails if the committed
spec is stale or the asset differs from it.

## Versioning

The app version is one number, stored once: `version.json` at the repo root.
Both the Python CLI (`main.py --version`, `version.__version__`) and this app
(`build.gradle.kts`) read it, so a release bump is a single edit:

* `versionName` = the string in `version.json` (e.g. `0.2.0`);
* `versionCode` is derived from it — `MAJOR*10000 + MINOR*100 + PATCH` (so
  `0.2.0` → `200`) — and must only ever be a monotonically increasing integer,
  which is why it is computed rather than hand-maintained.

To release, bump `version.json` and rebuild; never edit the numbers in
`build.gradle.kts`. Two other version strings exist and are deliberately
separate: `spec.json`'s `spec_version` (the data-schema / allow-list version)
and `CATALOGUE_VERSION` (the decoder catalogue). `tests/test_versioning.py`
pins all of this.

Remaining to wire up (needs a device or a follow-up):

* **Background sync** — uploads run after a collection pass and from the
  **Sync to cloud** button. Moving them onto WorkManager would also flush rows
  collected while the app is closed; today that queue waits for the next open.
* **Simulator provenance** — the Python collector labels a simulator adapter's
  rows `simulated` and keeps them out of the cloud. The phone currently has no
  equivalent `ATI` probe, so it writes everything `reported`.

## Safety (non-negotiable)

This app is **strictly read-only**. The only requests it can send are the
allow-listed ones in `spec.json` (`0x10 0x01`, `0x22`, `0x19` read sub-functions,
`0x3E`, OBD-II `0x01/0x03/0x09`). `uds/ReadOnlyGuard.kt` is the choke point and
must never be weakened; a port must not add a "send arbitrary bytes" API.
